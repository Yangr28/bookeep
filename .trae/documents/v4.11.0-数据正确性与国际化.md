# v4.11.0 实施计划:数据正确性 + 国际化基建

## Context

4.10.1 因严重问题被回滚,其想修复的 bug(预算刷新丢失、日期 UTC 偏差)仍在线上。经探查确认两个根因:

1. **预算丢失根因**:`budgetsSlice` 完全没接持久化层 —— `storage.ts` 有 6 类数据的 load/save,唯独没有 budgets,刷新/重启后预算必丢。
2. **日期 UTC 根因**:重要修正 —— `new Date(utcIso).getMonth()` 这类"UTC ISO → 本地字段"用法**本身正确**;真正的 P0 是 **15 处用 `toISOString()` 反推日期/月份键**的写法(UTC+8 早 8 点前键会错一天)。修复策略:**不改存储格式**(createdAt 保持完整 UTC ISO),只修派生逻辑。

同时用户新增需求:**国际化**(中文基准 + 英文,分阶段迁移)。

用户已确认:首发语言 = 中文 + 英文;文案迁移 = 分阶段(本版搭基建 + 迁移高频页面,其余后续版本)。

## 阶段 5:OCR 语言包下载可靠性(用户反馈:下载慢且常失败)

### 根因(已核实)

1. [ocrCache.ts](src/utils/ocrCache.ts) 用 **WebView 内 fetch** 下载大文件(chi_sim 语言包 10-20MB + wasm 引擎数 MB),下载后 base64 落盘 —— 无超时(连接卡死就永远转圈)、无断点保护、base64 转换内存翻倍
2. 候选列表首位是 `/ocr/*` **相对路径**(L15-17、L20-25):热更新页面上该路径 404,每次先白等一次失败才轮到慢速 CDN
3. 原生层已有带镜像切换 + 进度通知的下载器(`AppUpdatePlugin.downloadFile`,L401),但未暴露给 OCR 用

### 修复方案(涉及原生 → 本版为整包发布)

**Java 侧** `AppUpdatePlugin.java`:
- 新增 `@PluginMethod downloadOcrResources(call)`:接收 lang/worker/core 三个 URL 候选数组,复用现有 `downloadFile(candidates, target, kind)`(kind="ocr")逐一下载缺失文件,返回 ready 状态
- 顺带恢复被回滚的 **`.part` 临时文件 + rename 保护**(4.10.1 的 downloadOne 改造,防下载中断产生损坏文件;代码在 git 历史 024242e 中可参考)
- prepareOcrAssets 保持不变(内置 assets 复制仍是最优先路径,1-2 秒完成)

**TS 桥接** `src/plugins/appUpdate.ts`:
- 新增 `downloadOcrResources(options: { langUrls, workerUrls, coreUrls }): Promise<{ ready: boolean }>`
- `DownloadProgress.kind` 增加 `'ocr'`;web 桩抛错同现有模式

**JS 侧** `src/utils/ocrCache.ts`:
- 删除 `/ocr/*` 相对路径候选(热更新页面必 404;内置资源已由 prepareOcrAssets 原生复制覆盖)
- 新流程:原生平台且插件支持 `downloadOcrResources`(feature-detect)→ 全部走原生下载(缺失文件才下);旧基座无此方法 → 保留现有 JS fetch 兜底(并加 30s AbortController 单源超时)
- `downloadOCRData` 仅在原生平台被调用(已核实 ocrParser L258-280),浏览器分支不受影响
